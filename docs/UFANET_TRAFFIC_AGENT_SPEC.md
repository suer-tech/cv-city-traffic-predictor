# Спецификация для агента
## «Система мониторинга и прогноза пробок по скриншотам камер Уфанета»

Документ задаёт инженерный план реализации для автономных/полуавтономных агентов (в духе harness engineering).

---

## 1. Уточнённые вводные (зафиксировано с заказчиком)
- Первая версия должна быть **готова к запуску локально** и к **сбору данных** (скриншоты + подсчёт машин).
- Прогноз нужен в 2 разрезах:
  1. по каждой камере,
  2. по маршруту (агрегат из нескольких камер).
- Старт: 1 камера, целевой объём: 5–10, перспектива: ~100 камер.
- Стартовые данные:
  - `camera_id=1479988588`
  - `url=http://maps.ufanet.ru/ufa#1479988588`
  - `direction=SN` (временный маркер направления).
- MVP: считать **общий count по кадру** (без lane-level разбиения).
- Хранение изображений: постоянно хранить **1 скриншот в час** на камеру (для аудита качества).
- Окружение: локальный запуск, PostgreSQL, MLflow, только CPU (12 vCPU / 32 GB RAM).
- Надёжность capture: повторить 3 раза, затем логировать ошибку.
- Нужен ручной интерфейс (минимум): включение/выключение камеры и правка ROI.

---

## 2. Mission Brief и критерии успеха
**Цель:** устойчивый конвейер «скриншот → CV-метрики → временные ряды → прогноз 10/20/30 минут».  
**Ключ успеха v1:** система собирает данные, обучает модель на накопленных данных, выполняет инференс в заданном расписании, и сравнивает прогноз с фактом/прокси-фактом (включая Яндекс при доступности).

### 2.1 KPI первой версии
- Capture success rate: ≥ 95% слотов/сутки.
- Ingest latency (capture→DB): p95 ≤ 2 минуты.
- Forecast freshness: прогнозы доступны каждые 10 минут.
- Достоверность CV (MVP-порог, конфигурируемый):
  - относительная ошибка count (MAPE по ручной выборке) ≤ 35%.
- Достоверность Forecast (MVP-порог, конфигурируемый):
  - MAPE `vehicle_count` на горизонте 10 минут ≤ 30%,
  - на 20 минут ≤ 35%,
  - на 30 минут ≤ 40%.

> Пороговые значения вынести в конфиг для последующей настройки без изменения кода.

## 3. Архитектура (модульно)

```text
[orchestration/scheduler]
        |
        +--> [capture] ----> [hourly screenshot store]
        |          |
        |          +--> [ephemeral frame buffer]
        |
        +--> [vision] ------> [features]
        |                       |
        |                       v
        |                  [storage/postgresql]
        |                       |
        |                       +--> [forecast]
        |                       |        |
        |                       |        v
        |                       |   [predictions]
        |                       |
        |                       +--> [evaluation + mlflow]
        |
        +--> [admin ui: cameras + roi]
```

### 3.1 Модули и ответственность
1. `capture` — Playwright/Selenium, захват кадров, retry=3.
2. `vision` — детекция авто, общий count по кадру, quality score.
3. `features` — агрегация в 5-минутные интервалы + лаговые фичи.
4. `storage` — PostgreSQL (без Timescale в v1).
5. `forecast` — обучение/инференс по каждому camera и route.
6. `evaluation` — сравнение с фактом и внешним источником, лог в MLflow.
7. `orchestration` — расписание jobs, идемпотентный запуск.
8. `admin_ui` — ручное управление камерами и ROI.

## 4. Контракты данных

### 4.1 Справочник камер (`cameras`)
Поля (минимум):
- `camera_id` (PK)
- `source_url`
- `intersection_id`
- `direction` (например `SN`)
- `is_enabled` (bool)
- `roi_config` (jsonb)
- `created_at_utc`, `updated_at_utc`

### 4.2 Фактические метрики (`traffic_metrics_5m`)
Поля (минимум):
- `timestamp_utc`
- `camera_id`
- `intersection_id`
- `lane_id` (в v1 допустимо значение `all`)
- `vehicle_count`
- `density`
- `avg_speed_proxy` (может быть null в v1)
- `quality_score`
- `source_image_uri` (на hourly screenshot)

### 4.3 Маршруты (`routes`, `route_cameras`)
- `routes`: `route_id`, `name`, `is_enabled`
- `route_cameras`: `route_id`, `camera_id`, `order_index`

### 4.4 Прогнозы (`traffic_predictions`)
- `prediction_ts_utc`
- `target_ts_utc`
- `horizon_min` (10/20/30)
- `entity_type` (`camera` | `route`)
- `entity_id` (`camera_id` или `route_id`)
- `pred_vehicle_count`
- `pred_density`
- `congestion_probability`
- `model_version`
- `features_version`
- `explainability_payload` (jsonb: top features, SHAP summary)

### 4.5 Внешняя калибровка (`external_traffic_observations`)
- `timestamp_utc`
- `entity_type`
- `entity_id`
- `provider` (`yandex`)
- `traffic_score` (nullable)
- `source_status` (`ok`, `unavailable`, `not_configured`)
- `raw_payload` (jsonb)

## 5. Как обучать модель и как делать инференс

### 5.1 Режим обучения (v1)
- Тип: периодическое переобучение + fallback baseline.
- Частота: 1 раз в сутки (ночью, локальное время сервера).
- Минимальный объём данных для старта обучения:
  - рекомендуемо 7 суток,
  - минимум 3 суток для bootstrap.
- Обучающие данные: `traffic_metrics_5m` + календарные признаки + route-агрегаты.

### 5.2 Фичи (стартовый набор, конфигурируемый)
- Лаги `vehicle_count`: 1, 2, 3, 6, 12 интервалов (5 мин шаг).
- Rolling mean: 3/6/12 интервалов.
- Время: час, день недели, признак выходного.
- Качество кадра: `quality_score`.
- Для route-модели: агрегаты по камерам маршрута (sum/mean/max count).
- При доступности внешних данных: `yandex_score` как опциональная фича.

### 5.3 Модели (v1)
- Baseline: seasonal naive / rolling mean.
- Основная: XGBoost Regressor (CPU-friendly).
- Классификация пробки: логистическая модель или XGBoost Classifier по порогу congestion.

### 5.4 Расписание инференса
- Инференс выполнять **каждые 10 минут**.
- Каждый запуск формирует прогнозы на горизонты 10/20/30 минут.
- Прогнозы считаются для:
  - всех активных камер,
  - всех активных маршрутов.

### 5.5 Порог пробки (конфиг)
- `camera_congestion_threshold_count` — порог count на камеру.
- `route_congestion_threshold_count` — порог агрегированного count маршрута.
- Отдельно хранить внешний индикатор (Яндекс) и сравнивать его с модельным скорингом.

### 5.6 Интерпретируемость (обязательно)
- Для каждой модели логировать feature importance в MLflow.
- Для основной модели сохранять SHAP summary plot (если вычислительно допустимо на CPU).
- Для каждого прогноза хранить top-N факторов в `explainability_payload`.

## 6. Интеграция с Яндекс.Пробками

### 6.1 Текущее состояние
- API-ключа пока нет.
- В v1 интеграция реализуется как **адаптер-заглушка** с режимом `not_configured`.

### 6.2 После получения ключа
- Проверить, можно ли извлекать численный traffic score в рамках используемого API/лицензии.
- Если прямой score недоступен, хранить вычислимый прокси (например, цвет/уровень сегмента, если это разрешено условиями).
- Не блокировать основной pipeline при недоступности интеграции.

---

## 7. Оркестрация (v1)
1. Каждые 5 минут: `capture_job`.
2. После capture: `vision_job` + `feature_agg_job`.
3. Каждые 10 минут: `forecast_inference_job`.
4. Раз в сутки: `model_retrain_job` + `evaluation_job`.
5. Раз в час: `hourly_snapshot_persist_job` (сохранить 1 скриншот/час/камера).

---

## 8. Нефункциональные требования
- Масштабирование: от 1 до 10 камер без смены архитектуры.
- Производительность: CPU-only, без обязательного GPU.
- Надёжность capture: retry x3, затем error log + metric.
- Логирование: структурированные логи + MLflow.
- Идемпотентность: уникальные ключи и upsert в фактах/прогнозах.

---

## 9. План реализации по фазам

### Phase 0 — Setup (локально)
- Docker Compose: app + PostgreSQL + MLflow.
- Инициализация схемы БД и справочников.
- Регистрация стартовой камеры `1479988588`.

### Phase 1 — Сбор данных MVP
- Захват кадра каждые 5 минут.
- Подсчёт общего числа машин.
- Запись 5-минутных метрик в БД.
- Хранение 1 скриншота/час.

### Phase 2 — Прогноз MVP
- Построение фичей и baseline-модели.
- Обучение по накопленным данным (ежесуточно).
- Инференс каждые 10 минут (camera + route).
- Лог интерпретации и метрик в MLflow.

### Phase 3 — Калибровка и масштаб
- Подключение Яндекс-данных при наличии ключа.
- Калибровка порогов пробки.
- Рост до 5–10 камер.

## 10. Acceptance Criteria (обновлённые)
1. Система стабильно собирает данные по трафику и сохраняет их для обучения.
2. Есть автоматический обучающий цикл и отдельный цикл инференса.
3. Инференс выдаёт прогнозы по заданному диапазону времени (10/20/30).
4. Есть сравнение модельного прогноза с внешним индикатором (Яндекс) при его доступности.
5. Есть ручной интерфейс для управления камерами и ROI.

---

## 11. Что должен выдать агент в каждом PR
1. Какие предположения/пороги заданы в конфиге.
2. Какие метрики качества получены на текущих данных.
3. Какие ограничения остаются (например, нет API-ключа Яндекс).
4. Какой следующий шаг для роста точности прогноза.
