# Спецификация для агента
## «Система мониторинга и прогноза пробок по скриншотам камер Уфанета»

Документ задаёт инженерный план реализации для автономных/полуавтономных агентов (в духе harness engineering):
- что строить,
- в какой последовательности,
- какие интерфейсы и артефакты считаются обязательными,
- как проверять качество,
- какие риски контролировать.

---

## 1. Mission Brief (краткий бриф)
**Цель:** получить устойчивый конвейер «скриншот → CV-метрики → временные ряды → прогноз пробок 10/20/30 минут».  
**Основной сигнал:** число автомобилей и производные показатели плотности движения в зонах интереса.  
**Операционный контекст:** несколько камер, регулярный сбор данных, масштабирование по перекрёсткам.

### 1.1 KPI системы
- Технический KPI:
  - успешность получения кадров по расписанию ≥ 95%;
  - задержка обработки кадра (ingest→persist) ≤ 2 минут (p95).
- ML KPI:
  - MAPE / MAE прогноза по `vehicle_count` на горизонтах 10/20/30 минут;
  - отдельная метрика раннего обнаружения затора (precision/recall по бинарной метке congestion).
- Надёжность:
  - пайплайн не «падает целиком» при недоступности одной камеры;
  - деградация при внешних сбоях (Яндекс/API/страница) — контролируемая, с ретраями.

---

## 2. Область ответственности и границы

### 2.1 В scope
1. Плановый захват изображений с веб-страниц камер Уфанета.
2. Детекция/подсчёт автомобилей и расчёт интервальных метрик.
3. Хранение временных рядов и справочников камер/перекрёстков.
4. Обучение и инференс модели прогноза.
5. Оценка модели и мониторинг деградации.
6. (Опционально) интеграция с Яндекс.Пробками для калибровки/оценки.

### 2.2 Out of scope (первая итерация)
- Управление светофорами и real-time control контур.
- Полноценный high-availability кластер БД.
- Распознавание номеров/личных данных.

## 3. Референсная архитектура (модули)

```text
[Scheduler/Orchestrator]
        |
        v
[Capture Service (Playwright)] ---> [Raw Screenshot Storage]
        |
        v
[Vision Service (Detection/Tracking)]
        |
        v
[Feature Builder (5m aggregation)]
        |
        v
[PostgreSQL/Timeseries]
        |
        +--> [Forecast Service]
        |          |
        |          v
        |      [Predictions Table]
        |
        +--> [Evaluation Service + MLflow]
                    |
                    v
            [Dashboards / Reports]
```

### 3.1 Capture Service
**Задача:** headless-открытие URL камеры и вырезка ROI-области видео.

Требования:
- инструмент: Playwright (предпочтительно) или Selenium;
- периодичность по камере: default 5 минут (настраивается);
- метаданные кадра: `capture_ts_utc`, `camera_id`, `url`, `attempt`, `status`;
- сохранение скриншота в объектное хранилище/локальный volume с deterministic path.

### 3.2 Vision Service
**Задача:** детекция автомобилей (YOLO-подобная модель), опционально tracking для speed proxy.

Выход на кадр:
- `vehicle_count` (общий + по ROI/lane);
- `density` (например, count/ROI_area);
- `avg_speed_proxy` (из смещения треков между кадрами или эвристика `null`, если tracking отключён);
- `quality_score` (размытие/дождь/ночь/частичное закрытие кадра).

### 3.3 Feature Builder
Агрегация до интервала 5 минут:
- ключ: `timestamp_5m`, `camera_id`, `intersection_id`, `lane_id`;
- агрегаты: mean/max/p95 count, density, speed proxy;
- добавление календарных признаков: час, день недели, признак выходного.

### 3.4 Storage
Минимум 4 таблицы:
1. `cameras` — справочник камер (url, координаты, активность, ROI-конфиг).
2. `intersections` — справочник перекрёстков/направлений.
3. `traffic_metrics_5m` — фактические метрики по интервалам.
4. `traffic_predictions` — прогнозы и confidence.

Рекомендуется:
- PostgreSQL + Timescale extension (если доступно);
- индексы на (`camera_id`, `timestamp_utc`) и (`intersection_id`, `timestamp_utc`).

### 3.5 Forecast Service
Базовая стратегия:
1. baseline (naive seasonal / rolling mean);
2. tabular-модель (XGBoost/LightGBM) на лаговых признаках;
3. при достаточном объёме данных — LSTM/Temporal Fusion (опционально).

Горизонты прогноза:
- `t+10m`, `t+20m`, `t+30m`.

Целевые переменные:
- регрессия: `vehicle_count`, `density`;
- классификация: `congestion_probability`.

### 3.6 Evaluation + MLflow
Логировать:
- параметры эксперимента;
- версии данных и модели;
- метрики по каждому горизонту;
- feature importance / artifacts (графики ошибок, drift reports).

## 5. Оркестрация и расписание

Минимальная цепочка cron/оркестратора:
1. Каждые 5 минут: `capture_job`.
2. Через 0–1 мин после capture: `vision_job`.
3. Каждые 5 минут: `feature_agg_job`.
4. Каждые 5 минут: `forecast_inference_job`.
5. Раз в сутки: `model_retrain_job` + `evaluation_job`.

Рекомендуемые инструменты:
- Prefect/Airflow для DAG;
- fallback: APScheduler + отдельные workers.

---

## 6. Интеграция с Яндекс.Пробками (опционально)

### 6.1 Режимы использования
- **Feature mode:** текущий уровень пробок как дополнительный признак.
- **Calibration mode:** сравнение вероятности затора с внешним индексом.
- **Validation mode:** независимая метрика качества прогнозов.

### 6.2 Правила
- если API недоступен — пайплайн продолжает работу;
- пропуски маркировать явно (`yandex_score = null`, `ext_source_status = unavailable`);
- соблюдать юридические условия использования источника.

---

## 7. Нефункциональные требования
- Параллельная обработка камер (N workers).
- Горизонтальное расширение без рефакторинга ядра.
- Контейнеризация (Docker, docker-compose).
- Наблюдаемость: структурированные логи + MLflow + healthchecks.
- Идемпотентность: повторный запуск job не должен дублировать факты.

---

## 8. План реализации по фазам

### Phase 0 — Setup
- Инициализировать репозиторий сервиса и базовую структуру модулей.
- Поднять PostgreSQL + MLflow в docker-compose.
- Описать `.env.example` и конфиг камер.

### Phase 1 — Data Ingestion MVP
- Реализовать захват кадров 1–3 камер.
- Сохранение raw-скриншотов + метаданных.
- Настроить retry/backoff + алерты по ошибкам захвата.

### Phase 2 — CV MVP
- Подключить детектор автомобилей.
- Считать `vehicle_count` и `density` на интервале 5 минут.
- Сохранить в `traffic_metrics_5m`.

### Phase 3 — Forecast MVP
- Подготовить лаговые признаки.
- Реализовать baseline + XGBoost.
- Выполнять инференс на 10/20/30 минут.

### Phase 4 — Quality & Scale
- Добавить мониторинг drift и автоматическую валидацию моделей.
- Расширить до целевого числа камер.
- Добавить интеграцию с внешним индексом пробок.

---

## 9. Acceptance Criteria (Definition of Done)
Задача внедрения считается успешной, если:
1. Для каждой активной камеры создаются кадры по расписанию (не менее 95% слотов/сутки).
2. Метрики `vehicle_count`/`density` стабильно пишутся в БД без дубликатов.
3. Прогнозы на 10/20/30 минут доступны в отдельной таблице с версией модели.
4. В MLflow зафиксированы эксперименты и метрики по горизонтам.
5. Есть эксплуатационная документация запуска и восстановления.

---

## 10. Риски и стратегии снижения
- **Нестабильная веб-страница камеры** → fallback-сценарии селекторов, ретраи, watchdog.
- **Плохие погодные/ночные условия** → quality score + исключение низкокачественных кадров из обучения.
- **Сдвиг домена (ремонт дорог, сезонность)** → периодическое дообучение и drift-мониторинг.
- **Недостаток размеченных данных** → начать с pre-trained detector + выборочная ручная валидация.

1. Обновлённый ADR/документ решения.
2. Список изменённых модулей и миграций.
3. Отчёт по тестам и quality checks.
4. Ссылка на MLflow-run/артефакты.
5. Известные ограничения и следующий шаг.
