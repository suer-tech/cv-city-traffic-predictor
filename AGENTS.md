# AGENTS.md — правила работы агентов в этом репозитории

Этот файл задаёт базовый контракт для любых инженерных агентов, которые реализуют систему
мониторинга и прогноза пробок по скриншотам камер Уфанета.

## 1) Цель агента
Реализовывать модульную Python-систему, которая:
1. Снимает скриншоты страниц камер Уфанета по расписанию.
2. Вычисляет транспортные метрики из изображений (vehicle count, density, speed proxy).
3. Сохраняет метрики во временные ряды.
4. Строит прогноз загрузки/затора на горизонтах 10/20/30 минут.
5. Сравнивает прогноз с фактом (включая Яндекс.Пробки, если источник доступен).

Подробная спецификация: `docs/UFANET_TRAFFIC_AGENT_SPEC.md`.

## 2) Обязательные архитектурные принципы
- Соблюдать модульность: `capture` / `vision` / `features` / `storage` / `forecast` / `evaluation` / `orchestration`.
- Минимизировать связность между модулями через явные интерфейсы и DTO.
- Все критичные параметры выносить в конфигурацию (YAML + env overrides).
- Любой шаг пайплайна должен быть перезапускаемым и идемпотентным.
- Для длительных операций обязательно логирование и метрики выполнения.

## 3) Контракт данных (минимум)
- Гранулярность хранения: интервал 5 минут.
- Минимальные поля метрик:
  - `timestamp_utc`
  - `camera_id`
  - `intersection_id`
  - `lane_id`
  - `vehicle_count`
  - `density`
  - `avg_speed_proxy`
  - `source_image_uri`
  - `quality_score`
- Запрещено менять семантику этих полей без миграции схемы и обновления документации.

## 4) Ожидаемое поведение агента при реализации задач
1. Прежде чем писать код, обновить/создать ADR или техдок с объяснением решения.
2. При добавлении нового модуля:
   - создать README модуля,
   - описать вход/выход,
   - добавить пример запуска.
3. При изменениях в схеме БД:
   - добавить миграцию,
   - описать rollback,
   - обновить раздел схемы в документации.
4. При изменениях моделей прогноза:
   - зафиксировать фичи,
   - описать протокол валидации,
   - зафиксировать baseline-метрики.

## 5) Определение готовности (Definition of Done)
Задача считается выполненной, если:
- Код проходит линтеры/тесты.
- Для нового функционала есть минимум один автотест.
- Обновлена релевантная документация.
- В логах/MLflow видны ключевые этапы пайплайна.
- Изменения воспроизводимы через Docker Compose.

## 6) Стандарты качества
- Python 3.11+.
- Стиль: type hints, dataclass/pydantic для контрактов данных.
- Ошибки внешних интеграций (веб-страница камеры, API пробок) обрабатывать ретраями + backoff.
- Временные метки хранить в UTC.
- Никаких «магических» констант внутри бизнес-логики — только через конфиг.

## 7) Безопасность и правовые ограничения
- Не хранить персональные данные, не связанные с задачей транспортной аналитики.
- Хранить только необходимые артефакты (скриншоты/метаданные) с контролируемым retention.
- Учитывать условия использования внешних источников (Уфанет/Яндекс).
